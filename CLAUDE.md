# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Package manager: **bun** (`bun.lock` is the source of truth; `package-lock.json` is also present but bun is preferred).

```bash
bun install            # install dependencies
bun run dev            # vite dev server (SSR via TanStack Start)
bun run build          # production build (Cloudflare Worker output)
bun run build:dev      # build in development mode
bun run preview        # preview a production build
bun run lint           # eslint (typescript-eslint + react-hooks + prettier)
bun run format         # prettier --write .
```

No test runner is configured.

Deploy target is **Vercel via Nitro**. `vite build` writes the generic Nitro output to `.output/`. When the `VERCEL=1` env var is set (Vercel injects this automatically during its build), Nitro switches to the Vercel preset and emits **Vercel Build Output API v3** at `.vercel/output/` — `config.json`, the SSR serverless function at `functions/__server.func/`, and static assets at `static/`. Vercel auto-detects that directory and ignores the dashboard's framework preset; no `vercel.json` is needed.

## Architecture

This is a **TanStack Start** (SSR React 19) app deployed to **Vercel** (via Nitro), backed by **Supabase**. It is a HEALTHBIT/RDsaúde obesity-care dashboard (UI is pt-BR) tracking participants' weight/IMC/circumference across months.

### Lovable-managed Vite config — do not duplicate plugins
`vite.config.ts` uses `@lovable.dev/vite-tanstack-config` which **already wires**: `tanstackStart`, `viteReact`, `tailwindcss` (v4), `tsConfigPaths`, `componentTagger` (dev-only), `VITE_*` env injection, the `@/*` → `src/*` alias, React/TanStack dedupe, error-logger plugins, and sandbox detection (port/host/strictPort). Adding any of these manually will break the build with duplicate-plugin errors. Extra config goes through `defineConfig({ vite: { … } })`.

Important option flags in `vite.config.ts`:
- `cloudflare: false` — disables the preset's optional Cloudflare plugin (the project is no longer on Cloudflare Workers).
- `plugins: [nitro()]` — adds the Nitro plugin for Vercel deployment. Nitro auto-detects `VERCEL=1` and emits Build Output API v3.

The project was previously on Cloudflare Workers with a custom `src/server.ts` worker entry and an h3-error-normalization wrapper (`src/lib/error-capture.ts`, `src/lib/error-page.ts`). Those files were removed during the Vercel migration — error handling now defaults to TanStack Start's built-in behavior. There is no `wrangler.jsonc` and no Cloudflare-specific code.

### Routing
File-based via TanStack Router. **`src/routeTree.gen.ts` is auto-generated — never edit by hand.** The plugin regenerates it from `src/routes/*.tsx` during dev/build.

Routes:
- `/` (`routes/index.tsx`) — main dashboard, redirects to `/login` if no session
- `/gestao` (`routes/gestao.tsx`) — CRUD for participantes/medicoes; gated to `gestor_saude` or `admin`
- `/admin` (`routes/admin.tsx`) — role management + audit log; gated to `admin`
- `/login` (`routes/login.tsx`) — supabase email/password auth
- `routes/__root.tsx` wraps everything in `QueryClientProvider` + `AuthProvider`, mounts `AppSidebar` for all paths except `/login`

Route gating is done **client-side** in each route's component via `useAuth()` + `useRoles()` with `navigate({ to: … })`. The sidebar (`src/components/app-sidebar.tsx`) also hides items based on roles. Server-side enforcement lives in Supabase RLS policies — never rely on UI gating for security.

### Supabase clients — three variants, pick deliberately
- `src/integrations/supabase/client.ts` — **browser** client. Reads `import.meta.env.VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` (falls back to `process.env.SUPABASE_*` for SSR). Lazy via Proxy. Use this for normal authenticated user queries — RLS applies.
- `src/integrations/supabase/client.server.ts` — **service-role** client. Bypasses RLS. Only import from `*.server.ts` files or server functions. Never reach for this just to "make things work" — it disables the security model.
- `src/integrations/supabase/auth-middleware.ts` — `requireSupabaseAuth` TanStack Start middleware that validates an `Authorization: Bearer …` header via `supabase.auth.getClaims` and injects an authed client into the function context.

Both `client.ts` and `client.server.ts` are headed `// This file is automatically generated. Do not edit it directly.` — they are regenerated by the Lovable Cloud Supabase connector. If you need to change auth behavior, edit `auth-middleware.ts` or call sites, not the generated files.

ESLint blocks `import "server-only"` (Next.js convention) — for server-only modules, use the `*.server.ts` filename suffix or `@tanstack/react-start/server-only`.

### Data model & domain logic
Schema (in `supabase/migrations/`):
- `participantes` — one row per person: `id, numero, nome, altura, peso_inicial, imc_inicial, circunferencia_inicial, mes_inicio, ativo`
- `medicoes` — monthly readings, unique on `(participante_id, mes_referencia)`. Columns: `peso, imc, circunferencia, medicamento, dose, consultas_endocrino, consultas_nutri, consultas_psico, consultas_edfisica, observacao`. IMC is stored, not computed by the DB — `calcImc()` in `src/lib/dashboard-data.ts` is a client-side helper only.
- `user_roles` — enum `app_role` ∈ {`admin`, `gestor_saude`, `gestor`}. The SQL `has_role(uuid, app_role)` security-definer function backs every RLS policy that gates writes.
- `role_audit_log` — every grant/revoke (written from `routes/admin.tsx`)
- `configuracoes` — key/value settings (e.g. `mes_inicio`)
- Trigger `on_auth_user_created_role` auto-assigns `gestor` to new signups — **caveat**: per `.lovable/plan.md`, this trigger may not exist in the TI-managed Supabase project; the first admin must be assigned manually via SQL Editor (`INSERT INTO public.user_roles (user_id, role) VALUES ('<uuid>', 'admin')`).

`src/lib/dashboard-data.ts` is the central data layer: `fetchAll()` returns both tables, plus pure helpers `calcImc`, `calcEvolucaoGrupo`, `calcMarcos`, `mesesDistintosInicio`, `formatMes`. Charts and KPI cards consume the output of these — keep aggregation logic here rather than scattering it across components.

### UI conventions
- **shadcn/ui** in `src/components/ui/` (style: new-york, base: slate, icons: lucide). Configured in `components.json`. Aliases: `@/components`, `@/components/ui`, `@/lib`, `@/lib/utils`, `@/hooks`. Add new shadcn components via the CLI rather than hand-writing into `ui/`.
- Tailwind v4 (`@tailwindcss/vite`); global styles in `src/styles.css` (linked from `__root.tsx` via `?url`).
- Class composition via `cn()` from `@/lib/utils` (clsx + tailwind-merge).
- Toaster: `sonner` (mounted in `__root.tsx`).
- Forms: `react-hook-form` + `zod` + `@hookform/resolvers`.
- Bulk import: Excel parsing via `xlsx` (see `src/components/dashboard/UploadDialog.tsx`).
- All user-facing copy is pt-BR.

### Environment variables
Required at runtime:
- Client/SSR: `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` (Vite replaces at build time; falls back to `process.env.SUPABASE_URL` / `SUPABASE_PUBLISHABLE_KEY` for SSR)
- Server-only: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (used by `client.server.ts` and `auth-middleware.ts`)

For Vercel deploys these must be configured in the Vercel project's Environment Variables dashboard (the local `.env` file is not uploaded). `VITE_*` vars must be set at **Build** time, not just Runtime, because Vite inlines them at build.
